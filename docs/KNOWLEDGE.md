# Ability knowledge base

The companion's situational intelligence is data-driven. Nothing in the
scheduler branches on a hard-coded spell id; every decision flows through:

```
decoded v5 frame (spell id + combat context)
  → AbilityCatalog lookup (by spell id)
  → AbilityDefinition (purpose, tier, GCD, range, conditions, groups)
  → PolicyEvaluator (USE / HOLD / SKIP + reason)
  → ActionScheduler (rank, pacing, failure recovery)
  → executor (PostMessage to the game window)
```

MaxDps stays the only rotation source. The knowledge base never says "cast
this spell"; it says **what kind of ability this is** and **which observable
conditions must hold before the companion is allowed to press it**.

## AbilityDefinition fields (v2.6.0 registry)

See `AbilityModel.cs` for the exact record. Every field has a safe default
per category; a curated entry only lists what it changes. No silent generic
default: an entry without meaningful intelligence is labeled Incomplete or
Unknown and cannot drive automatic situational use (see enforcement below).

### v2.7.0 coverage axes (orthogonal, derived unless curated)

- **ownership** — Companion / MaxDps / Shared / Manual / Unavailable: who owns
  the when-to-use decision. Derived deterministically: manual wins; the
  class-spell tail is MaxDps; interrupts / self-sustains / gap closers are
  Companion; defensives are Shared (MaxDps surfaces, companion gates);
  main/offensive/consumable/trinket are MaxDps. Curated `ownership` wins.
- **completeness** — Complete / Partial / Delegated / ManualByDesign /
  Unobservable / ResearchPending / LiveUnverified: how good that knowledge is.
  Delegated follows MaxDps ownership; manual is ManualByDesign; verified or
  researched rules are Complete; derived conservative rules are Partial;
  unsafe automation is Unobservable; modeled rows are ResearchPending.
- **delegation** — a `[Flags]` set (MainRotation / RotationOrdering /
  ResourceOptimization / ProcInteraction / TalentInteraction /
  ComplexBuffWindow / TargetSelectionUnavailable / EnemyCountUnavailable /
  SecretValueLimitation / MaxDpsAlreadyModelsThis / NotWorthDuplicating /
  InsufficientObservableContext). **Mandatory for every MaxDps-owned entry**;
  a bare unexplained MaxDpsOnly is an audit violation. Derived from category +
  usage; curated arrays win (e.g. Recklessness = RotationOrdering +
  ComplexBuffWindow).
- **manualReason** — mandatory for every manual entry: CC target state /
  debuff identity / enemy buff identity / threat state / ally state /
  raid coordination / safety rule / user choice / other.
- **patch metadata** — `introducedPatch` (curated only), `sourcePatch`
  (defaults to the catalog patch 12.1), `lastValidatedPatch`, `sourceType`
  (DerivedModel / VendorPin / Curated / Research / LiveClientDb2),
  `sourceUrl`, `sourceConfidence` (Unknown/Low/Medium/High), `liveVerified`.
  **Stale** (both source and last-validated older than the supported patch)
  and **newer than supported** entries are audit violations — stale
  intelligence can never silently drive the runtime.
- **relations** — expanded to 27 kinds (Replaces / ReplacedBy / Alias /
  Duplicate / TalentVariant / HeroTalentVariant / SpecVariant / HistoricalId /
  PairsWith / Supersedes / RequiresBuff / RequiresTargetState /
  RequiresResourceState / RequiresTalent / RequiresHeroTalent /
  SharesWindowWith / DoNotStackWith / ...). Spell ID is the canonical
  identity — entries are never merged by display name; known cases (Spell Lock
  19647 → 119910, Avenging Wrath 31884 / 231895) are documented id-keyed.

Legacy policy fields (unchanged semantics):

- **purpose** — Rotational / MajorOffensive / MinorOffensive /
  DefensiveMajor / DefensiveMinor / Immunity / Absorb / Reflect / SelfHeal /
  Interrupt / GapCloser / Escape / Movement / Dispel / External /
  Consumable / Trinket / Unknown.
- **tier** — None / Minor / Major / Immunity. Drives defensive sequencing
  (smallest sufficient mitigation first). Any non-survival purpose is
  normalised to None so it can never block a real defensive.
- **minimumUrgency** (derived) — the lowest MaxDps defensive urgency at which
  the ability may fire automatically: `Major`/`Immunity` default to `Red`,
  `Minor`/`None` to `Yellow`. A live MaxDps recommendation of the *exact*
  ability lowers the requirement by one stage but never below Yellow
  (`minimumUrgencyCurated` records whether the value was curated, in which
  case the recommendation discount does not apply — see Ignore Pain 190456,
  curated Orange).
- **urgencySource** — `Hp` (default; the vendor HP curve) or `Stagger`
  (Purifying Brew 119582; the reversed stagger curve with the vendor's HP
  fallback). See `AbilityModel.cs` for the full stage definitions.
- **gcd** — OnGcd / OffGcd / Unknown. Only a VERIFIED non-movement off-GCD
  ability bypasses the cast/channel execution-safety hold: `GcdVerified` is
  set when the value is curated, or for the intrinsically off-GCD
  Interrupt/Consumable/Trinket categories. An uncurated defensive's OffGcd
  default is a guess and stays held under a cast/channel. Gap closers /
  movement are never exempt (movement cancels a cast).
- **range / targetRange** — static hints; the runtime range comes from the
  protocol's per-slot probe. `OutOfMelee` is required for gap closers.
- **cdMs / durMs** — approximate sequencing hints (overlap windows). They
  are NOT game timers: exact cooldowns are secret/ never read.
- **healPct** — static curated estimate of the heal as a fraction of the
  player's maximum health (e.g. Impending Victory = 30). It is a policy
   heuristic, never a live read and never exact: the solo layer uses it for
   the overheal guard (`missing < ceil(healPct * 0.6)` holds the heal as
   mostly wasted) and never claims the actual amount healed. `0`/absent =
   UNKNOWN → no overheal guard; the HP thresholds still apply. When the HP
   source is the Ext2 HP curve (hidden plain HP), the guard uses the band's
   UPPER bound (`HpPctUpper`) so quantisation cannot justify an overheal.
   Percentages
  come from the live tooltips/Wiki (sources in the research doc) and are
  marked when they describe a patch older than 12.1.
- **requiresEnemyCast** — reflect-type abilities: without an observed
  incoming cast the policy holds (UnknownPolicy `Hold` by default).
- **useBelowHpPct / holdAboveHpPct** — HP gates (e.g. Lay on Hands below
   20%; Word of Glory covers the 20–65% sustain band).
- **holdWhenBuffActive** — skip when the ability's own aura is already on
  the player (default true for defensives).
- **neverAutomatic** — externals, escapes, dispels and movement utility are
  never fired automatically. Gap closers are exempt (the policy still needs
  a confirmed out-of-melee target + in-range ability).
- **conflictGroup / priority** — sequencing groups (`DR.Major`, `DR.Minor`,
  `DR.Magic`, `Immunity`, `Absorb`, `Heal.Emergency`, `Trinket.OnUse`, …).

Registry fields (v2.6.0; all derived where possible - see
`docs/research/ABILITY_REGISTRY.md` for the derivation rules):

- **abilityKind** — ActiveCombatAbility / Passive / Aura / TalentModifier /
  InternalSpell / QuestSpell / ProfessionSpell / NonCombatAbility /
  Deprecated / Unknown. Only active combat abilities plus curated manual
  utilities drive behaviour.
- **intelligenceStatus** — Unknown / Incomplete / MaxDpsBacked /
  CompanionRule / ConservativeSafety / Heuristic / ResearchBacked / Verified /
  ManualByDesign / UnsafeToAutomate.
- **automationContext** — Autonomous / MaxDpsOnly / Manual.
- **maxDpsRelationship** — NotSurfaced / MainRotation / OffensiveBucket /
  DefensiveBucket / InterruptBucket / ConsumableBucket / TrinketBucket.
- **opportunityCost** — Unknown / Low / Medium / High / Critical (derived
  from tier + cooldown).
- **interruptKind** — Dedicated / Silence / Stun / Displacement / Incapacitate
  (derived Dedicated; curated Silence for 15487 / 119910).
- **offensiveUsage** — MajorBurst / MinorBurst / ShortCooldown / Execute /
  AoeOnly / SingleTargetOnly / ProcDriven / ResourceDriven / WindowDriven /
  DefensiveOffensiveHybrid / Summon / Transformation / Manual (derived from
  purpose + cooldown; vendor-only rows may stay Unknown = delegated to
  MaxDps).
- **mobilityKind** — GapCloser / Disengage / Teleport / SpeedBurst /
  MovementImmunity / Escape.
- **abilityRequirements** flags; **talentNote / heroTalentNote**;
  **patchVerified** (gamePatch 12.1 / interface 120100).
- **relations** — Requires / Enhances / Replaces / ConflictsWith /
  SynergizesWith / Consumes / Protects / Follows / Precedes.
- **capabilityTags**; **enemyCountMin** (enforced only for
  companion-backed offensives - MaxDps-backed rows delegate); **holdForBurst**.
- Derived: CooldownClass / TargetKind / EmergencyCapability / capability
  flags / AutomationAllowed / HasIntelligence / ManualByDesign.

Policy verdicts are five-state: Use / Hold / Skip / Unavailable / Unknown
(out-of-range = Unavailable; context-unknown = Unknown; see
`docs/research/ABILITY_REGISTRY.md`). The scheduler counts Hold + Unknown as
held, Skip + Unavailable as skipped; only Use is scheduled.

Enforcement ("no silent generic default" rule): Incomplete / Unknown /
UnsafeToAutomate entries can never be generated by companion-only slots
(Mobility / SelfHeal, Defensive gap-fill) - verdict Skip; on MaxDps slots
they keep exactly the pre-registry Generic path. Manual-by-design is
structural (NeverAutomatic maps to Automation.Manual); OFF stays absolute.

Versioning / patch guard: `AbilityCatalog.ExpectedGamePatch "12.1"`,
`ExpectedInterfaceVersion 120100`, `ExpectedMaxDpsVersion 11.3.49`,
`CatalogVersion 3`; a curated file stamped with another patch throws at
load. `--ability-audit=<path>` writes the audit report;
`--ability-info=<spellId>` inspects one entry (app-side equivalent of
`/mdb ability`); `tools/ability_audit.ps1` runs the audit plus the addon
Catalog.lua drift check.

## Curation rules

1. **Vendor first.** Ids, names and categories come from the pinned MaxDps
   snapshot for the current game version. Never invent a spell id.
2. **Conservative defaults.** Uncurated entries keep category defaults:
   defensives fail open on unknown HP, offensives fire when MaxDps says so,
   movement holds.
3. **Mark uncertainty.** `source: "vendor-only"` / `note` text for entries
   that could not be cross-checked against a current source. Skewed
   cooldown/duration values are sequencing hints only.
4. **No secret reads, ever.** The knowledge base is static data; nothing in
   it may require an API that can return a secret value. Runtime probes live
   in `Reader.lua` behind pcall + scrub.
5. **Extras are per spec.** Mobility/SelfHeal lists are ordered by
   preference; the bridge offers the first entry that is ready AND has a
   resolvable keybind (v2.2) — an unbound talent cannot shadow a bound
   alternative. Both sides read the same generated `Catalog.lua`, so they
   can never disagree. The extras are the only source of self-sustain
   candidates MaxDps itself never surfaces; anything MaxDps already puts in
   a slot is handled there and is not duplicated.
   **SelfHeal2 (v3.0.0):** the bridge encodes the NEXT distinct ready+bound
   self-heal candidate in the Ext2 cells 36–38; the companion evaluates it as
   an alternate for the same SelfHeal slot only when the primary does not Use
   (e.g. Lay on Hands held by its ceiling → Word of Glory). Rank and the
   one-action-per-tick rule are unchanged.
   **aliases (v3.0.0):** a top-level `aliases` block (e.g. 202168 ↔ 34428,
   19647 ↔ 119910) is stored symmetrically and emitted as
   `MDB.SpellAliases`; the bridge resolves a bar/macro variant id through it.
   Extras ids are checked against `spell-verification.json` names.
   **cooldown / reset awareness (r2):** the bridge encodes a self-heal only
   while it is off cooldown and re-reads readiness EVERY tick — readiness is
   never cached across ticks (only keybind resolution is memoised, and that
   cache is dropped on bar/binding/talent/spec events including
   `SPELL_UPDATE_COOLDOWN`). A dynamic reset that makes the same spell ready
   again is therefore offered within the next tick. Companion side: a ready
   SelfHeal is never stale-demoted (unchanged slot content after a cooldown is
   a new opportunity, not a stuck suggestion) and a transient failed press is
   suppressed for at most 1.5 s with no escalating backoff; a permanent
   exclusion (policy OFF / unbound / unknown) keeps its existing behaviour.
   When HP is in the sustain window and no heal is ready, the scheduler holds
   with the distinct reason `SelfHealCoolingDown` (`waiting for self-heal
   cooldown`) instead of a generic no-candidate, so the UI/telemetry explains
   the wait.
   **resetHint (optional):** a curated free-form string such as
   `"resets on kill"` may be added per ability; it is informational only
   (surfaced in telemetry), never read by any decision rule.
6. **The defensive extras are DERIVED, not hand-listed.** Unlike
   Mobility/SelfHeal, `Catalog.lua`'s per-spec `defensive` list is computed
   by `AbilityCatalog.DefensiveGapFill`: every vendor-listed defensive for
   the class+spec that is survival-purpose, not `NeverAutomatic`, and not a
   full immunity, ordered Major before Minor/None, then curated `priority`,
   then ascending spell id (deterministic). It is only a gap-fill — the
    bridge uses it only when MaxDps names no bound defensive AND the observed
    HP urgency is Red, and the whole path stays inside MaxDps's
    `enableDefensives` switch. Catalog revision is 3 (`--gen-catalog`), and
    the committed file is pinned by tests.
7. **The offensive extras are CURATED, not derived.** `Catalog.lua`'s
   per-spec `offensive` list is authored in `abilities.json` under
   `extras.<class>.<spec>.offensive`, unlike the derived defensive list. This
   is deliberate: the vendor `classCooldowns[class][spec].offensive` bucket
   mixes true damage-burst windows with rotational/resource fillers, so a
   blind derivation would let the companion fire a filler. Selection rule:
   **only true offensive cooldowns (damage burst windows), 1-4 per spec,
   ordered shared burst first then spec-specific, never rotational fillers
   and never utilities.** Every id must be present in
   `spell-verification.json` with a matching live-client name (test-pinned).
   Example: Warrior Arms `[107574 Avatar, 228920 Ravager, 262161 Warbreaker]`
   (Avatar/Ravager are shared across specs; Warbreaker is Arms-specific). The
   task's legacy Ravager id `152277` is not in the 12.1 DB2 export and is
   corrected to the verified `228920`.

## Defensive automation (v2.3 / v3.0.0 Orange tier)

MaxDps owns the defensive *trigger*; the companion adds the urgency stage,
the user policy and the gap-fill. Nothing here replaces MaxDps's rotation.

- **Trigger.** `MaxDps:GlowDefensiveHPMidnight` flags a defensive while the
  player is alive and the spell is usable/enabled, and renders it through a
  3-point HP colour curve (Red at 0.3, Yellow at 0.5, transparent at 1.0).
  The bridge stages that rendered colour into `DefensiveUrgency`
  (White/Yellow/Orange/Red/Unknown) at the curve's own control points; a
  per-spell special case (Purifying Brew 119582) uses the reversed stagger
  curve with the vendor's HP fallback. The urgency nibbles are **additive on
  the v5 wire** (reserved and always `0` before bridge 2.3) and the version
  nibble stays 5, so an updated addon still decodes with a pre-2.3 companion
  exe. Full derivation and citations:
  `docs/research/ABILITY_RESEARCH.md` §6.
- **Gates** (`PolicyEvaluator.Defensive`): White holds every automatic
  defensive (hard rule). Majors/immunities need Red unless the ability is the
  exact MaxDps-recommended Defensive slot candidate (one-stage discount,
  never below Yellow, not applied to a curated `minimumUrgency`, and not to
  Escape/Movement/External). Minors need Yellow. Unknown holds majors and
  keeps minors on the pre-urgency gates. Emergency HP
  (`Solo.EmergencyHpPct`, default 35) overrides. Escape/Movement (even when
  user-enabled) and External are emergency-only. Dispel holds (debuff state
  is not observable).
- **Gap-fill (v2.3 Red / v3.0.0 Orange).** `MDB.GetDefensiveCandidate()`
  returns the MaxDps flagged + ready + bound defensive first; only when MaxDps
  names none does the generated Catalog.lua list supply the first ready +
  bound entry, with the cell 31 B bit0 source flag set. At **Red** the major
  list (`defensive`) is offered; at **Orange** the short-cooldown list
  (`defensiveMinor`, Minor/None-tier mitigation only) is offered, so a
  user-enabled short CD can fire at Orange while a major still waits for Red
  (`MinimumUrgency` Red for major/immunity). A gap-fill is never offered below
  Orange, a major gap-fill never fires above Red, and the whole path stays
  inside MaxDps's `enableDefensives` switch.
- **One dispatcher.** The whole path stays in the existing policy + scheduler
  pipeline: one defensive candidate per tick, one send path, the scheduler
  state machine unchanged.

## Offensive automation (v3.0.0)

Before v3.0.0 the Offensive slot was MaxDps-wire-only: a cooldown the user
toggled ON never fired when MaxDps did not surface it. The companion now has a
gap-fill seam for it, mirroring the defensive pattern but with
offensive-appropriate gates:

- **Source.** `MDB.GetOffensiveCandidate()` returns MaxDps's own flagged +
  ready offensive first; when MaxDps names none, the curated per-spec
  `offensive` list supplies the first ready + bound entry. The whole path stays
  inside MaxDps's own `enableCooldowns` switch. There is **no wire source bit**
  (PixelProtocol decode is frozen and every slot-flag bit is used), so the
  companion derives `CandidateSourceKind.CompanionGapFill` by id membership in
  the same generated list (`AbilityCatalog.IsOffensiveGapFill`); see
  `docs/PROTOCOL.md` for why this is replay-safe (class/spec are recorded in
  the telemetry policy block).
- **Gates** (`CandidateProviders.OffensiveCandidateProvider`, unchanged
  reason strings for MaxDps-sourced rows): a gap-fill candidate is offered only
  in combat **or** in Solo mode — never out of combat in Normal mode; the
  own-buff skip, the curated pairing window (`OffensiveActive`/`HoldForBurst`),
  the curated `EnemyCountMin` AoE guard, the melee/range gates and the
  cast/channel execution-safety gate all still apply. One action per tick and
  the existing offensive rank are unchanged.
- **User policy.** OFF stays absolute (the gap-fill never overrides it); ON is
  eligibility only. `[Abilities] Modes` (SoloOnly/NormalOnly/Manual/Never)
  still apply.
- **Registry.** A companion-generated offensive gap-fill whose intelligence is
  Incomplete/Unknown/UnsafeToAutomate is structurally skipped, exactly like the
  other companion-only sources; the curated lists only contain entries that are
  catalogued with real intelligence.

## TTK estimator + gates (v3.2.0)

The companion estimates per-target time-to-kill (TTK) and uses it to stop
wasting cooldowns. Nothing new is observed: the estimator consumes the target HP
band already on the wire (cell 29) plus the frame clock.

- **Estimator (`Knowledge/TtkEstimator.cs`).** Pure and fake-clock. `frac =
  (band + 0.5) / 15`. It RESETs (new epoch) on no target, on HP unknown for
  more than 10 s, or when `frac` jumps UP by more than 0.12 (new target / big
  heal). It feeds only real declines (`inst = (prevFrac - frac) / dt`, ignored
  below 0.004 frac/s as noise) into an EWMA with a 3 s time constant. A valid
  estimate needs ≥2 fed samples, a ≥2.5 s observation span and `ewma ≥ 0.004`;
  `TtkSec = clamp(frac / ewma, 0, 300)` (a trickle reads as 300 s "long"). An
  invalid estimate **fails open**: every TTK gate is skipped, because holding a
  cooldown on an unknown target is exactly the DPS loss the feature avoids.
- **Plumbing.** `RotationEngine` owns one estimator and feeds it once per real
  frame, before the policy. The result is attached to the policy's
  `CombatContext` (`WithTtk`) so no scheduler signature changes. `[TimeToKill]
  Enabled=0` disables the estimator and skips all gates. Target HP is still
  never used for anything but the estimator; the plain percent is reconstructed
  from the band for the execute gate.
- **Defaults (`Knowledge/TtkPolicy.cs`).** When `abilities.json` has no curated
  `minTtkSec`, the usage default applies: MajorBurst 12 s, Transformation/Summon
  20 s, WindowDriven 10 s, ShortCooldown/ProcDriven/AoeOnly/SingleTargetOnly/
  ResourceDriven/Execute 5 s, DefensiveOffensiveHybrid 0 (never gate), unknown
  10 s.
- **Gates (`CandidateProviders`).**
  - **T1 waste guard (Offensive, all sources):** valid TTK below the ability's
    minimum ⇒ Hold `"target ~Xs to die; saving <name> (needs Ns)"`. MaxDps
    re-suggests next tick — no lockout.
  - **T2 two-uses (Offensive):** valid TTK ≥ `2·cd + dur` (curated cooldown;
    absent cooldown skips the rule) ⇒ bypass the pairing hold and fire.
  - **T3 execute (Offensive):** `executeFavored` and valid target HP ≤
    `executeBelowPct` ⇒ bypass the pairing hold and fire. `executeBelowPct`
    without `executeFavored` is inert documentation.
  - **T4 dying target (Defensive, Solo only):** not emergency and valid TTK
    below 6 s ⇒ Hold `"target dies in ~Xs; saving <mitigation>"`. Emergency HP
    always overrides; group scope is a follow-up because other enemies are
    unobservable.
- **Schema.** `minTtkSec` (number, optional), `executeBelowPct` (0–100,
  optional) and `executeFavored` (bool, optional) are parsed by
  `AbilityCatalog` into `AbilityDefinition`. Curation is owned by the T-B
  workstream; T-A only parses.

## User ability policy (`[Abilities]`)

`Knowledge/AbilityPolicy.cs` stores an immutable explicit ON/OFF override per
spell id on top of the curated default (`NeverAutomatic`):

- **OFF is absolute.** An ability turned OFF never fires automatically —
  urgency, a MaxDps recommendation, Solo mode and emergency HP cannot
  override it; the verdict reason is `user policy disabled`.
- **ON is eligibility, not spam.** It only makes the ability eligible for the
  normal gates; White still holds, tier/urgency/range/cast safety still
  apply. A user may explicitly enable a manual-by-design ability (e.g.
  Vanish), which then keeps the emergency-only rule.
- **Storage.** `settings.ini` `[Abilities]` `On=` / `Off=` are comma
  lists of spell ids; an entry is only written when it differs from the
  curated default, so the file stays a diff (an override equal to the
  default is dropped). User modes (`Modes=id:Mode` -
  SoloOnly / NormalOnly / Manual / Never / Always / Automatic; Always
  currently evaluates as Automatic, reserved) are persisted by AppSettings;
  ON/OFF stays the UI surface. The "Class skills" screen is the generated UI over
  this policy (class → spec → ability with metadata; see below); each
  checkbox persists through `AbilityPolicy.With(...)` and `AppSettings.Save`.

## Class-spells layer

The pinned vendor snapshot carries a third, purely informational table of
class abilities: `vendor/MaxDps/SpellData.lua`'s retail `ns.classSpellData`
block is a flat `class -> spec -> token -> spell id` map. It has **no names,
no categories and no active/passive flag** — it is a raw token list, not a
curated CD table. The companion merges it as the lowest-priority knowledge
layer so the Class skills screen can offer a toggle for abilities that
neither vendor `Cooldowns.lua` nor `abilities.json` names.

- **Extraction.** `tools/Extract-ClassSpells.ps1` (PowerShell 7,
  `pwsh -File tools/Extract-ClassSpells.ps1`) parses that block with a
  brace-depth reader and ignores the Cata/Mists `ns.classSpellData` blocks
  below it. It writes `app/MaxDpsCompanion/Knowledge/class-spells.json`
  (schema `{class, spec, token, id}` only) with **8070 entries, 3566 distinct
  spell ids, 13 classes and 39 class/spec pairs**; Demon Hunter's new
  "Devourer" spec has no rows in the vendor table. The script is
  deterministic (byte-identical reruns) and the companion embeds the JSON as
  a resource. The vendor snapshot remains read-only input.
- **Name decoding.** `ClassSpellBook.DecodeName` decodes CamelCase tokens
  best-effort into display labels ("SinisterStrike" → "Sinister Strike",
  "TricksoftheTrade" → "Tricks of the Trade", "ThousandCuts" → "Thousand
  Cuts", "CoupdeGrace" → "Coup de Grace"), with a small alias map for tokens
  that decode badly (Odyn's Fury, Take 'Em By Surprise, Chosen's Revelry,
  Death's Arrival, …). The decode is only a fallback: when the live-client
  verification (below) covers the id, the client's own official name wins
  (e.g. "Sinister Strike"). Anything the curated/vendor layers already carry
  keeps that layer's real name instead.
- **Junk/passive filter.** The vendor table mixes active abilities with
  passive talents, professions, riding, heirlooms and old-content perks.
  `ClassSpellBook.IsJunk` drops exact tokens and name patterns
  (`Improved*`, `*Specialization`, `Mastery*`, `*Riding*`, `*Pathfinder*`,
  `*Chemistry*`, `Poisons/Poisoner`, `Guild*`, `Hearth*`, and a curated
  passive-talent long tail). Junk rows stay in the generated JSON; they are
  simply never merged or shown. The list is maintained with the
  `--dump-class-skills` CLI (below).
- **Merge priority.** `AbilityCatalog.Load(vendor, curated, classSpells)`
  merges in the order curated > vendor `Cooldowns`/`interrupts` > class-spells
  layer; the 2-argument overload keeps the pre-class-spell behaviour for
  tests. `AbilityDefinition.Provenance` is `Vendor | Curated | ClassSpell`.
  Ids the live-client verification marks unverified are skipped entirely (see
  below), so a class-spell id that no longer exists in 12.1 can never enter
  the merged catalog.
  `DefensiveGapFill` deliberately ignores `ClassSpell` entries, so the
  bridge's generated `Catalog.lua` and its runtime defensive gap-fill cannot
  widen through a modeled layer. Movement tokens stay `NeverAutomatic`
  (manual/emergency-only if enabled); Main/Offensive/Defensive default ON.
- **Toggles.** A class-spell row is toggled per spell id through the existing
  `[Abilities] On=`/`Off=` settings lists — no new INI section. OFF is the
  absolute automatic-use prohibition (for a Main-slot spell it means "this
  suggestion is skipped; the scheduler falls through to the next suggested
  stroke", never a rotation rewrite); ON is eligibility only.
- **Maintenance.** `MaxDpsCompanion.exe --dump-class-skills=<path>` writes
  `CLASS<TAB>SPEC<TAB>section<TAB>provenance<TAB>name<TAB>id` for every
  class/spec (shared rows plus each Main/Offensive/Defensive/Movement
  section), which is how the junk/passive list is curated.

Honest limits. Classification and name decoding are modeled best-effort: the
vendor data has no active/passive flag, so passive talents that evade the
filter can still appear (their toggles are inert because such spells never
arrive as suggestions). Demon Hunter Devourer has no vendor class-spell rows
(the screen still lists its catalog/extras abilities). No live in-game
validation has been claimed for this layer.

### Verification against the live client

The class-spells layer is the only knowledge source with no names or
active/passive flag, so it is cross-checked against the live retail client's
own data:

- **Tool and sources.** `tools/Verify-ClassSpells.ps1` (PowerShell 7,
  `pwsh -File tools/Verify-ClassSpells.ps1`) streams three
  [wago.tools](https://wago.tools) DB2 CSV exports — `SpellName`, `SpellMisc`
  and `ManifestInterfaceData` — and writes
  `app/MaxDpsCompanion/Knowledge/spell-verification.json`. The output is
  deterministic (byte-identical reruns).
- **Semantics and counts.** One entry per distinct class-spell id: the
  client's official `Name_lang`, its icon slug, and a `verified` flag
  (whether the id still exists in `SpellName` and is not a marked-deprecated
  name). On this pin the file holds **3566 entries — 3515 verified / 51
  absent** (removed in 12.1).
- **Unverified ids are dropped, not guessed.** `ClassSpellBook` marks each
  entry `Verified`, and `AbilityCatalog.MergeClassSpells` skips any entry
  whose live-client fact says the id is gone. The official name/icon are used
  when present; the decoded CamelCase name is only a fallback for ids the
  verification does not cover.
- **Column and slug notes (live-verified 2026-09-28).** `SpellMisc`'s `ID`
  column is the misc-record id, not the spell id — the real spell id is the
  trailing `SpellID` column (joining on `ID` yields wrong icons). The manifest
  file names can contain spaces (e.g. `Warlock_ Healthstone`), so the CDN
  request strips them (`warlock_healthstone`). Wowhead's tooltip endpoints
  are blocked from this machine; wago.tools plus Blizzard's render CDN are the
  working official sources.
- **Icons.** The tool downloaded **3510** official icons into
  `dist/assets/icons/{spellId}.jpg` and the dev bin cache
  (`app/MaxDpsCompanion/bin/Release/net8.0-windows/win-x64/assets/icons`).
  The runtime `SpellIconCache` prefers the official slug from the
  verification (one request to the render CDN) and only falls back to tooltip
  discovery. `build.ps1` preserves `settings.ini` and `assets/` across
  publishes, so the cache survives rebuilds.

## What the policy CANNOT do (honest limits)

See `docs/research/ABILITY_RESEARCH.md` §4 and its v2.1 addendum:

- **Enemy cast identity** is not observable: in 12.x `UnitCastingInfo` is
  secret for non-player units, and combat-log events are not available to
  addons. Reflect filtering therefore uses "a cast is live" only — an AoE or
  unreflectable cast cannot be told apart from a reflectable one, so Spell
  Reflection may be spent on a cast it cannot return (it still applies its
  magic DR). Spell identity is never fabricated.
- **Enemy cast importance** is not observable, so interrupts fire on every
  cast the sensors let through; the bridge DOES veto an explicitly
  non-interruptible observation, and the policy skips a stale suggestion.
  There is no "save the kick for the dangerous cast" logic.
- **Immune targets** are not observable (no flag in any safe API); a press
  the game rejects is handled by failure recovery (escalating suppression),
  not by knowledge.
- **Movement / position** (XYZ, facing, ground effects) is not observable;
  gap closers only fire when the target is confirmed out of melee and the
  ability is confirmed in range, and escape/repositioning utilities are
  never automatic.
- **Resource state** (rage/energy/chi/holy power) is not in the protocol;
  MaxDps's readiness gate owns it (`C_Spell.IsSpellUsable`).
- **Debuff types** for dispels are not observable; dispels stay manual.
- **Ally state** beyond the player is not in the protocol; externals stay
  manual.
- **Exact cooldowns / absorbs / DR stacks** are secret or unobservable;
  overlap checks use the companion's own send history plus curated
  duration hints. A stale (v4/v1) addon session loses the defensive
  sequencing/trinket-pairing memory entirely (spell ids are absent) while
  still firing fail-open.
- **Target HP is a band, not a measurement.** The coarse 0..14 target-HP band
  (cell 29) feeds only the TTK estimator (v3.2.0); the plain HP percent is
  reconstructed from the band for the execute gate, and no defensive/offensive
  rule treats it as exact. Player HP is UNKNOWN whenever the client hides it,
  and the solo layer then conserves rather than guesses.
- **Telemetry**: the policy record exists only for ticks where the
  scheduler actually ran (`pol.fresh=true`); legacy-path ticks are recorded
  without a policy block instead of a stale plan.
